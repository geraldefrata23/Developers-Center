# ShopeePay Developers Center

A documentation site for two unrelated ShopeePay products — the **SNAP API**
(QR payments, hosted Checkout, Link & Pay, Disbursement) and the **AirPay
Gateway Service API** (hosted-checkout redirect gateway) — each with a live
"Try It" sandbox panel on every endpoint page.

## Why per-product folders

Both the frontend content and the backend routing config are split one
file per product (Access Token, Disbursement, CPM, MPM, Checkout with
ShopeePay, Account Linking, Link & Pay, Link & Pay (API Based), Gateway
Service), with backend and frontend logic staying in their own separate
trees throughout. The goal: mapping any one product to its functional test
documentation, or handing just that product to someone to review, means
pointing at one folder — not grepping through a 1000-line file. Adding a
new endpoint to an existing product touches exactly two files (that
product's `content.ts` and its `config/endpoints/*.js`); adding a whole new
product means one new folder on each side plus one new line in the two
`index` aggregators.

## Building

The frontend is TypeScript, compiled to native ES modules the browser loads
directly — no bundler, no dev server.

```bash
npm install
npm run build          # tsc -p frontend/tsconfig.json  ->  frontend/dist/
npm start               # runs the build, then starts the BFF on :4000
```

`npm run dev` does the same but with `node --watch` on the backend. There's
no `tsc --watch` wired into that yet — re-run `npm run build` (or
`npm run build:watch` in a second terminal) after editing anything under
`frontend/src/`.

Since there's no bundler, every relative import in `frontend/src/**/*.ts`
is written with an explicit `.js` extension (e.g. `from "./dom.js"`) even
though the source file is `.ts` — that's not a typo, it's what
`moduleResolution: "NodeNext"` requires so the *emitted* JS has valid,
directly-loadable import paths. `tsc` still resolves it back to `dom.ts`
for type-checking.

## Running it

```bash
export SNAP_BASE=https://api.snap.uat.airpay.co.id      # optional, this is the default
export AIRPAY_BASE=https://api.gw.uat.airpay.co.id       # optional, this is the default
npm start                                                  # http://localhost:4000
```

`server.js` serves the frontend (including `frontend/dist/`) and the
`/api/sandbox/*` BFF from the same origin/port, so there's nothing else to
run.

### Environment variables

| Variable | Default | Purpose |
|---|---|---|
| `PORT` | `4000` | BFF port |
| `ALLOWED_ORIGIN` | `*` | CORS allow-list, comma-separated. Set this before deploying anywhere real. |
| `SNAP_BASE` | `https://api.snap.uat.airpay.co.id` | SNAP sandbox host |
| `AIRPAY_BASE` | `https://api.gw.uat.airpay.co.id` | AirPay Gateway sandbox host |
| `DEBUG_SANDBOX_CALLS` | `false` | Set to `true` to log every outbound request/response server-side |
| `SNAP_CHANNEL_ID` | `95251` | Value sent as the `CHANNEL-ID` header on hmac/hmac-get calls |

## Routing

Every page has its own URL — `/`, `/snap/:id`, `/gateway/:id` — via the
History API (`core/router.ts`). `backend/server.js` falls back to
`index.html` for any unmatched path, so a hard refresh or a shared link to
e.g. `/snap/link-balance-inquiry` lands directly on that page instead of
bouncing back to the landing chooser. This is also why `index.html`'s
script tag and stylesheet link use absolute paths (`/dist/core/main.js`,
not `dist/core/main.js`) — a relative path would resolve against
`/snap/...` and 404.

## Credentials are scoped per product

SNAP and AirPay Gateway credentials are stored completely independently —
separate in-memory state, separate localStorage keys
(`spp_docs_credentials_snap_v1` / `spp_docs_credentials_gateway_v1`), and
separate modal views. `Credentials.get()` always resolves to whichever
product is active (`App.mode`) at call time; there is no shared/global
credential object. Each modal also has a Reset button that clears just
that product's saved values — a stand-in for real per-user credential
management until this page grows actual authentication.

## Security notes

This is a **sandbox convenience tool**, not a secrets vault:

- Credentials entered under "My Credentials" are stored in the browser's
  `localStorage` (see `core/credentials.ts`) purely so you don't retype
  them every visit. They never touch any server except the BFF, and only
  for the single request you trigger by clicking "Send to Sandbox."
- The BFF (`backend/services/snapClient.js`) does not persist credentials
  anywhere — they arrive in the request body, get used once to sign and
  call the sandbox, and are discarded when that request finishes.
- `accessToken` (from Get Access Token) and `accountToken` (from Account
  Binding) are the two exceptions: both are kept in an in-memory JS
  variable for the current browser tab only — never written to
  `localStorage` — so the Try It panel can pre-fill them on later calls
  without asking you to copy/paste a token around.
- **Don't use this tool with production credentials.** The credentials
  modal says to ask the ShopeePay Product Team for UAT credentials instead.
- All sample request/response payloads shown in the docs use fictional
  data (`acme_*` merchant/store ids, `Jane Doe`, `DEMO STORE`, etc.) —
  nothing from any real Postman environment or partner account ships in
  this reference.

## Try It defaults

When a Try It panel builds its default request body (`core/tryit.ts`,
`buildDefaultBody`), fields fall into three buckets:

1. **Identity fields** (`merchantId`, `storeId`, and their various
   `*ExtId` / `*_ext_id` spellings across products) — pre-filled from
   whatever you've saved under My Credentials, since you'll want the same
   merchant/store on almost every call.
2. **Linked-account fields** (`accountToken`) — pre-filled automatically
   once you've completed Account Linking (Get Auth Code → Account
   Binding) in this browser tab, the same way `accessToken` is.
3. **Everything else transaction-specific** (amounts, reference numbers,
   QR content, redirect URLs, …) — deliberately left blank. These are the
   fields you're actually testing, and silently prefilling them with
   sample data tends to hide bugs rather than catch them.

## Adding a new endpoint to an existing product

1. Add its routing/signing metadata to that product's file under
   `backend/config/endpoints/` (`method`, `path`, `base`, `sign`, and
   `pathParamName` if it has a path parameter).
2. Add its documentation entry to the `endpoints` map in that product's
   `frontend/src/products/**/content.ts` — the object key **must** match
   the id used in step 1.
3. Add a `{id, label, method}` entry to that file's `nav.items` so it
   shows up in the sidebar.
4. `npm run build`.

## Adding a whole new product

1. New folder under `frontend/src/products/snap/` (or `gateway/`) with a
   `content.ts` exporting `nav` and `endpoints` (and `staticPages` if it
   has non-endpoint pages).
2. New file under `backend/config/endpoints/` with that product's routing
   metadata, and one line added to `backend/config/endpoints/index.js`.
3. One import + one line in each of the three arrays/objects in
   `frontend/src/products/snap/index.ts` (or `gateway/index.ts`).

No route handler to write on the backend either way — `routes/sandbox.js`
is generic and dispatches on `endpointId`.
